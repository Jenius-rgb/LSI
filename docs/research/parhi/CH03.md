## 1. Concepts, in our words

### 3.1 Two ways to go faster (pp. 63–64)

- For the direct-form 3-tap FIR filter the sample period is at least one multiply and two adds,
  `T_sample ≥ T_M + 2T_A` (eqs. 3.2–3.3). If the application needs a faster sample rate, the structure
  must change.
- **Pipelining** puts registers into the datapath so the critical path gets shorter and the clock can go up.
- **Parallel processing** copies the hardware so several samples are handled per clock.
- Both can instead be used to save power at the same speed (section 3.4).

### 3.2 Pipelining (pp. 64–69)

- Two extra registers in the FIR filter cut the critical path from `T_M + 2T_A` to `T_M + T_A`; two
  consecutive outputs are then in flight at the same time (Fig. 3.3, Table 3.1).
- Costs: more registers, and latency. In an M-level pipeline, every input-to-output path has M − 1 more delays
  than before (p. 66).
- The clock period is set by the longest path between registers, or between a register and an I/O.
- **Rule** (p. 66): pipeline registers may only be placed on a **feed-forward cutset**, and on *every* edge
  of that cutset. A cutset is a set of edges whose removal splits the graph in two; it is feed-forward if all
  its edges point the same way. Example 3.2.1 (pp. 66–68): a graph pipelined with registers on only some edges
  of a cutset reaches the shorter critical path but computes something else; the fix is to register all edges
  of the cutset.
- **Data-broadcast structure** (pp. 68–69): transposing the FIR graph gives the same critical path
  `T_M + T_A` with no extra registers; the input goes to all multipliers at once.
- **Fine-grain pipelining** (p. 69): split the multiplier itself into two parts (10 time units as 6 + 4) and
  register between them, so the clock period can drop to `(T_M + T_A)/2` (Fig. 3.8).

### 3.3 Parallel processing (pp. 69–74)

- Turn the single-input single-output filter into a multiple-input multiple-output one: with block size L,
  each clock takes L inputs and gives L outputs (eq. 3.5 for L = 3). A register in a block system delays by
  L samples ("block delay", L-slow).
- The clock period is unchanged (`T_clk ≥ T_M + 2T_A`, eq. 3.6), but
  `T_iter = T_sample = T_clk / L` (eq. 3.7). In a pipelined system T_clk equals T_sample; in a parallel one it
  does not.
- Serial-to-parallel and parallel-to-serial converters sit at the ends (Figs. 3.11–3.13).
- **Why parallelism at all** (p. 71): pipelining stops helping once the clock is limited by I/O (pad and
  board wire delay, e.g. 8 ns between two chips). The system is then communication bound, and only
  parallelism raises the rate further. Both can be combined: fine-grain pipelining inside a 3-parallel filter
  gives `T_sample = T_clk/3 = (T_M + 2T_A)/6` (eq. 3.8, Fig. 3.15).
- Parallelism with a slow clock also saves clock-network power compared with a fast pipelined clock; very fine
  (bit-level) pipelining costs many registers and much latency (p. 74).

### 3.4 Same speed, less power (pp. 74–82)

- First-order models: delay `T_pd = C_charge·V0 / (k(V0 − Vt)²)` (eq. 3.9); power `P = C_total·V0²·f`
  (eq. 3.10).
- Pipelining by M divides the capacitance charged per cycle by M, so at the same clock the supply can drop to
  βV0, with `M(βV0 − Vt)² = β(V0 − Vt)²` (eq. 3.15) and `P_pip = β²·P_seq` (eq. 3.12). Example 3.4.1:
  5.0 V → 3.0165 V, power 36.4 % of the original (pp. 75–76).
- L-parallel processing gives each path L times longer: `L(βV0 − Vt)² = β(V0 − Vt)²` (eq. 3.23), power
  again β² of the original. Example 3.4.2 (2-parallel 4-tap FIR): 3.3 V → 2.174 V, 43.41 %. Example 3.4.3:
  an area-efficient 2-parallel filter with 6 instead of 8 multipliers reaches about the same power (43.6 %)
  with less area (pp. 79–81).
- Combined: `ML(βV0 − Vt)² = β(V0 − Vt)²` (eq. 3.43); for L = M = 2, V0 = 5 V, Vt = 0.6 V, β ≈ 0.4 and power
  falls to about 0.16 (p. 82). Noise margins and process limits put a floor under the supply.

### 3.5–3.6 Conclusions and problems (pp. 82–89)

- Fewer than L times the multipliers is possible for parallel FIR filters with fast algorithms (chapter 9);
  recursive filters need look-ahead (chapter 10). Problems cover cutset placement, block filters, 2D FIR
  broadcast forms, interleaving two recursions on one pipelined multiply–add (problem 8), and the
  power/area trade-offs of block size.

## 3. What this means for SENTINEL

1. **Pipelining the two critical paths** [VIVADO-STA facts from `CH02.md` section 3]. The worst setup paths at
   125 MHz are the LUT multiplier (operand register → `p_reg`) and the C3 checksum-weight adder tree. Both are
   feed-forward, so fine-grain pipelining (Fig. 3.8) applies: split the 8 × 8 multiplier into partial products
   and a final add with a register between, and add a register level to the C3 tree. [INFERENCE] The cutset
   rule is the trap: the control bits that travel with the product (`v2`, `l2`, `f2` in `rtl/lane_lut.v`), all
   K data lanes and all checksum lanes must get the same extra stage, or the checker compares sums that belong
   to different units. Example 3.2.1 is exactly this failure. Bit-exactness is not affected (same arithmetic,
   one cycle later); cycle counts and any test that fixes pipeline depth would change, which needs an ADR.
2. **Resources leave room for parallelism** [VIVADO-STA, `results/vivado/official/summary.json` and
   `impl_utilization_hier.rpt`]: 6851/14600 LUT, 6149/29200 FF, 2488/3650 slices (68.16 %), 14/45 BRAM
   tiles, **3/80 DSP**. The lane array (`u_lanes`, LUT multipliers) takes 1711 LUT and 1188 FF.
   [INFERENCE] SENTINEL's K lanes are already parallel processing over output channels. More throughput can
   come from more lanes or from DSP-based lanes (the RTL has `lane_dsp_full` and `lane_dsp_min`); the
   unused DSP slices are the cheapest place for it. Slices (68 %) will run out before LUTs (47 %), so a
   larger K has to be checked by an implementation run, not by LUT count. A K change also changes the C2/C3
   checksum widths (weights k and k²), which are parameters already.
3. **I/O bound** (p. 71) [INFERENCE]. End to end, an image must cross the SPI link (speed [UNKNOWN], board
   fact) or JTAG. If that transfer takes longer than the compute, faster lanes do not shorten the demo
   latency. The report must keep on-chip cycles (`CYCLES_TOTAL`) and end-to-end time apart, as
   `board/BRINGUP_NO_PI.md` step 9 already says.
4. **Voltage scaling is out of scope.** Section 3.4 lowers the supply voltage; CLAUDE.md section 8 forbids
   changing any voltage, and VCCINT on ZERO7 comes from the board. Only the delay model (eq. 3.9) is useful:
   path delay depends on supply voltage and on temperature through k and Vt, which is why an overclocked
   lane can pass at one temperature and fail at another, and why the governor keeps margin and reads the
   XADC temperature [INFERENCE; the size of this effect on ZERO7 is [UNKNOWN] until measured].
5. **Block processing over pixels** [INFERENCE]. Eq. 3.5 computes L outputs of the same filter per clock.
   For SENTINEL that would be two output positions per cycle sharing each weight fetch; it doubles the MACs
   but not the weight bandwidth. Chapter 8–9 (fast convolution) can cut the MAC count of such a block
   below 2×; to be weighed there.

Candidates noted for the development list: fine-grain pipelining of the multiplier and the C3 tree (Should,
raises f_safe margin); DSP-based or more lanes (Should/Could, needs an implementation run); keep on-chip and
end-to-end timing apart in the report (Must, documentation).
