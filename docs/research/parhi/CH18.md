## 1. Concepts, in our words

### 18.1–18.2 What a programmable DSP is (pp. 695–697)

- Programmable DSPs (PDSPs) are microcomputers specialised for arithmetic-heavy signal processing, first built around 1980
  for real-time speech. Compared with the general microprocessor of the day they had a hardware multiplier and several
  memories; the book's table puts the first generation at 5 M multiply–adds per second against 100 K for a contemporary
  microprocessor, at similar power (Table 18.1).

### 18.3 The two defining features (pp. 697–702)

- **Data path**: a multiplier fused with an accumulator so that a MAC completes in one instruction cycle, an ALU, shifters
  for scaling, and saturation arithmetic that clamps to the largest positive or negative value on overflow instead of
  wrapping. Address arithmetic runs in separate address generation units, in parallel with the data path.
- **Memory architecture**: one MAC per cycle needs several memory accesses per cycle (coefficient, sample, instruction), so
  PDSPs use Harvard and modified Harvard organisations, several banks, dual-ported memories, register-indirect and modulo
  addressing, and caches (pp. 699–701).
- Pipelined PDSPs are programmed either in time-stationary style (the programmer schedules each pipeline stage) or in
  data-stationary style (one instruction describes everything done to one set of operands; the tools schedule it).

### 18.4 DSPs for wireless (pp. 703)

- Generations differ mainly in bus structure and memory bandwidth (Table 18.2). Wireless parts favour domain-specific
  data paths over wide VLIW/SIMD: two MACs plus an arithmetic unit, restricted input combinations, and instructions such as
  square-distance-accumulate (vector quantization), add–compare–select (Viterbi) and Galois-field operations.

### 18.5 Media processors and multimedia extensions (pp. 704–714)

- Multimedia code uses small integer operands, regular compute-heavy loops, heavy memory traffic with reuse, and complex
  control in the light parts. Responses: SIMD and MIMD multiprocessing; **subword parallelism** (a wide ALU split into
  several narrow ones, e.g. four 16-bit adds in one 64-bit add, with carries blocked at the boundaries); (V)LIW
  instruction-level parallelism scheduled by the compiler; special instructions; coprocessors next to a RISC core.
- Examples: a MIMD chip with four DSPs and a RISC core on a crossbar, VLIW/SIMD media processors, and a VLIW DSP whose
  compiler reaches about 84 % of hand-written assembly efficiency (p. 711). Microprocessor extensions (MMX, MAX) add
  subword instructions; multiplication is the hard part, since a multiplier costs three to four times an adder's area and
  about three times its latency (p. 713).

### 18.6 Conclusions (pp. 714–715)

- Requirements: flexibility, high throughput, low power and cost; software radio and programmable digital TV as targets.

## 3. What this means for SENTINEL

1. **Memory bandwidth must follow any throughput increase** [INFERENCE]. Each SENTINEL cycle needs one activation byte and K
   weight bytes (`docs/SPEC.md` 5.2). Every speed-up candidate (K = 16, two operands per lane, Winograd tiles) multiplies that
   demand, and block RAM ports, not multipliers, may then set the limit. The current design uses 13 RAMB36 and 2 RAMB18
   ([VIVADO-STA], `results/vivado/official/impl_utilization_hier.rpt`). Each candidate's ADR must state its memory width and
   port count, not only its multiplier count.
2. **Saturation where it matters, none where it cannot happen.** SENTINEL saturates only at requant (`docs/SPEC.md` 3.3) and
   sizes accumulators so they cannot overflow (`CH11.md` item 2), which is the PDSP practice applied to a fixed design.
3. **Packing two INT8 products into one DSP slice is not needed** [INFERENCE]. Subword parallelism has an FPGA form: with a
   shared operand (SENTINEL's broadcast activation), one wide multiplier can produce two products at once if the weights are
   packed into one operand with a guard gap. With 77 of 80 DSP slices unused ([VIVADO-STA]), even K = 16 plus three checksum
   lanes needs only 19 slices without packing, so the trick buys nothing here and would complicate the bounds and the
   checksum lanes. Recorded, not proposed.
4. **SENTINEL already has the PDSP split of data path and address generation.** The operand generator (`u_gen`, 777 LUT,
   [VIVADO-STA]) plays the role of the address generation unit; it also holds the checksum-weight generator, whose tree is
   the worst path in `clk_safe_raw` (`CH13.md`, `CH15.md`).
5. **Coprocessor model.** SENTINEL is a dedicated coprocessor next to a host (Raspberry Pi over SPI, or the PC over JTAG,
   ADR-025), the arrangement the book describes in 18.5.1.5 and, for systolic arrays, in chapter 7.
